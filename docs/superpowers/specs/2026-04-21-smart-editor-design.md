## 1. 项目概述

### 1.1 项目背景

信息安全行业的售前和商务团队在日常工作中需要频繁编写投标文件、技术方案、商务提案等文档。这些工作存在以下痛点：

- **重复劳动多**：相似项目需要重复编写大量相同内容
- **知识分散**：历史经验和优秀案例分散在 NAS 服务器各处（约 80GB、上万文件），难以快速检索
- **需求理解耗时**：客户需求文档（招标文件、需求规格书）篇幅长，人工提炼要点效率低
- **格式要求严**：投标文档对格式规范要求严格，偏离表需逐条核对，人工检查效率低且易遗漏废标项
- **时间压力大**：投标截止日期紧迫，需要快速产出高质量文档

### 1.2 项目目标

开发一款 Tauri 桌面端智能文档助手，以侧边栏形式辅助 Word/WPS 使用，实现：

1. **需求智能解析**：上传客户需求文件后自动提取技术要点
2. **知识资产化**：将历史文档转化为可复用的卡片模板，支持四维分类检索
3. **智能辅助写作**：根据需求要点自动搜索知识库，推送相关历史片段，一键生成技术方案草稿
4. **一键规范检查**：自动检测偏离项、废标风险、格式规范、术语一致性
5. **知识持续沉淀**：新文档脱敏后可加入模板库，形成良性循环

### 1.3 目标用户

| 用户角色 | 核心需求 | 使用场景 |
|---------|---------|---------|
| 售前工程师 | 快速编写技术方案 | 投标技术方案编制 |
| 商务人员 | 规范商务文档、检查偏离项 | 投标文件商务部分编制 |
| 项目经理 | 统一文档标准、团队协作 | 项目文档管理和审核 |

### 2.2 技术选型

| 层级 | 组件 | 选型 | 理由 |
|-----|------|------|------|
| **桌面框架** | 主框架 | Tauri (Rust + WebView) | 包体极小（< 10MB），原生跨平台（Win/Mac），内置文件系统权限 |
| **前端** | UI 框架 | React + TypeScript | 组件生态成熟，团队易维护 |
| **前端** | 富文本编辑器 | Tiptap (ProseMirror) | 专业级富文本，AI 指令生态成熟（`/` 菜单、划线菜单），易扩展 |
| **前端** | 样式 | Tailwind CSS | 快速构建统一风格界面 |
| **后端** | Rust 后端 | Tauri Command + Tokio | 与前端深度集成，无需独立服务进程 |
| **检索** | 全文搜索引擎 | Meilisearch（内嵌进程） | 启动快、中文分词优秀、支持过滤/排序/高亮 |
| **数据** | 元数据存储 | SQLite | 零配置、单文件、跨平台 |
| **文档解析** | docx | `docx-rs` / `mammoth` | Rust/JS 原生解析，无需 Python 依赖 |
| **文档解析** | pdf | `pdf-extract` / `lopdf` | 提取纯文本用于索引和 AI 分析 |
| **AI** | 本地 LLM | Ollama + qwen2.5:14b / deepseek-r1:14b | 数据不出本地，隐私合规；局域网可共享访问 |
| **AI** | 云端降级 | Claude API / DeepSeek API | 本地机器配置不足时自动/手动切换，保证可用性 |
| **插入 Word** | 桥接方案 | 富文本剪贴板 + Office.js 可选插件 | 剪贴板兼容性最好；Office.js 插件用于深度集成场景 |

### 2.3 架构演进说明

相较于 v1.0（Office.js + Python FastAPI + SQLite FTS5）的改进：

| 维度 | v1.0 方案 | v2.0 方案 | 改进原因 |
|------|----------|----------|---------|
| 插件形态 | Office.js 任务窗格（受限多） | Tauri 独立侧边栏窗口 | Office.js 无法直接访问本地文件，需 Python 代理，部署复杂 |
| 本地服务 | Python FastAPI 独立进程 | Rust 内置于 Tauri | 无需用户安装 Python、配环境，单安装包双击运行 |
| 检索引擎 | SQLite FTS5 + ChromaDB | Meilisearch 内嵌 | Meilisearch 搜索体验更好，支持中文分词、容错拼写、相关性排序 |
| 部署方式 | 插件侧载 + 服务自启（复杂） | 单安装包（.exe / .dmg） | 用户零配置，IT 部门易分发 |
| 跨平台 | Office.js Mac 支持弱 | Tauri 原生 Win/Mac | 团队有 Mac 用户，需一致体验 |
| AI 降级 | 仅本地 Ollama | 本地优先 + 云端降级 | 低配机器也能正常使用 |

### 3.2 需求文件上传与分析模块（新增）

**功能描述**：用户将客户需求文档（招标文件、需求规格说明书等）拖入侧边栏，系统自动提取技术要点，基于知识库推荐相关模板和内容，一键生成技术方案草稿。

#### 3.2.1 文件上传与解析

- **支持格式**：`.docx`、`.doc`、`.pdf`、`.txt`
- **上传方式**：拖放至上传区，或点击选择文件
- **文件处理**：
  1. Rust 后端接收文件，保存至临时目录
  2. 调用文档解析引擎提取纯文本
     - `docx` → `docx-rs` 提取段落和表格文本
     - `pdf` → `pdf-extract` / `lopdf` 提取文本层
     - `txt` → 直接读取
  3. 对超大文件（> 50MB）进行分段提取，优先处理前 100 页
  4. 提取完成后删除临时文件，不保留原始文档

#### 3.2.2 AI 需求要点提取

- **触发**：解析完成后自动发送至 AI
- **Prompt 设计**：
  ```
  你是一位需求分析专家，擅长从招标文件和需求规格说明书中提取技术实现要点。

  请分析以下文档内容，提取所有技术实现要点。对每个要点：
  - 如果需求明确，直接列出
  - 如果需求模糊或需要确认，标注"[需确认]"并给出建议确认的问题

  输出严格的 JSON 格式：
  {
    "requirements": [
      {"id": 1, "text": "实现基于角色的访问控制（RBAC）", "certainty": "certain"},
      {"id": 2, "text": "支持5000+并发用户", "certainty": "uncertain", "note": "需确认是峰值并发还是平均并发"}
    ]
  }

  文档内容：
  [文档文本，控制在 8000 token 以内，超长则分段提取]
  ```
- **前端展示**：提取的要点以可勾选列表形式展示，用户可：
  - 勾选/取消勾选要点（仅勾选的要点进入后续流程）
  - 编辑要点文字
  - 删除要点
  - 添加自定义要点

#### 3.2.3 知识库关联推荐

- **触发**：用户确认要点列表后，自动执行
- **检索逻辑**：
  1. 将每个要点作为独立查询词，调用 Meilisearch 全文检索
  2. 合并去重，按相关度排序
  3. 返回 Top-10 结果
- **展示内容**：
  - 模板/文档标题
  - 所属分类（文档属性 × 业务领域 × 内容模块）
  - 相关度分数
  - 匹配片段预览（高亮关键词）
- **用户操作**：
  - 点击结果展开完整片段
  - 点击"引用"将片段加入"参考资料"列表
  - 多选参考资料用于生成文档

#### 3.2.4 技术方案草稿生成

- **触发**：用户点击"生成技术方案草稿"
- **输入组装**：
  - 用户确认的需求要点列表
  - 用户引用的知识库片段
  - 预设的文档框架（根据文档属性维自动选择）
- **Prompt 设计**：
  ```
  你是一位资深信息安全售前工程师，擅长编写技术方案文档。

  请根据以下信息生成一份完整的技术方案文档：

  ## 需求要点
  [勾选的要点列表]

  ## 参考资料
  [用户引用的知识库片段]

  ## 输出要求
  1. 文档结构：项目概述 → 需求分析 → 方案设计 → 实施计划 → 风险评估
  2. 技术描述专业、准确，符合等保/网络安全行业标准
  3. 对模糊需求给出合理的假设说明，并在文档中标注"[待确认]"
  4. 使用 Markdown 格式，标题层级清晰
  5. 内容详实，每个章节至少 200 字

  请直接输出文档内容。
  ```
- **输出处理**：
  1. AI 返回 Markdown 文档
  2. 前端在 Tiptap 编辑器中渲染为富文本
  3. 用户可直接编辑、增删、调整格式
  4. 点击"插入 Word" → 通过剪贴板（富文本 HTML）写入 Word/WPS

### 3.3 卡片化模板库模块

**功能描述**：将历史文档拆分为可复用的内容卡片，建立统一的模板库。

#### 3.3.1 四维分类模型

采用**四维分类模型**，支持多维度组合定位：

| 维度 | 取值 |
|-----|------|
| **文档属性** | 投标应答、技术方案、实施方案、合同协议、汇报材料 |
| **业务领域** | 网络安全、应用安全、数据安全、安全运营、安全管理 |
| **内容模块** | 技术方案、商务条款、实施计划、资质证明、偏离说明、案例介绍 |
| **项目阶段** | 方案阶段、投标阶段、合同阶段 |

**安全层级**（业务领域子维度）：检测层、防御层、分析层、治理层

#### 3.3.2 模板基础功能

| 功能点 | 说明 | 优先级 |
|-------|------|-------|
| 模板创建 | 从 Word 文档自动拆分生成卡片 | P0 |
| 模板分类 | 按四维分类体系组织 | P0 |
| 标签体系 | 多维度标签（如 #等保2.0 #三级 #偏离表） | P0 |
| 全文检索 | 支持关键词、标签、内容片段检索 | P0 |
| 智能推荐 | 基于当前编辑内容推荐相关模板 | P0 |
| 预览功能 | 插入前可预览卡片完整内容 | P1 |
| 收藏功能 | 常用卡片可收藏快速访问 | P1 |
| 版本管理 | 模板版本控制和更新提示 | P2 |

#### 3.3.3 数据模型

```sql
CREATE TABLE templates (
    id INTEGER PRIMARY KEY,
    title TEXT NOT NULL,
    content TEXT NOT NULL,           -- Markdown 正文
    content_html TEXT,               -- 预渲染 HTML，用于快速插入
    doc_attr TEXT,                   -- 文档属性
    business_domain TEXT,            -- 业务领域
    security_layer TEXT,             -- 安全层级
    content_module TEXT,             -- 内容模块
    project_phase TEXT,              -- 项目阶段
    tags TEXT,                       -- JSON 数组标签
    source_file TEXT,                -- 来源 NAS 文件路径
    source_para_range TEXT,          -- 来源段落范围
    created_at TIMESTAMP,
    updated_at TIMESTAMP,
    use_count INTEGER DEFAULT 0,
    rating INTEGER DEFAULT 0
);
```

### 3.4 智能内容推送模块

**功能描述**：根据用户当前编辑内容，智能推荐相关的历史模板和内容片段。

#### 3.4.1 推送模式

| 模式 | 触发条件 | 推送内容 | 适用场景 |
|-----|---------|---------|---------|
| **模式 A：智能识别触发** | 检测到特定关键词（如"等保测评""渗透测试"） | 相关历史方案段落 | 编写过程中实时辅助 |
| **模式 B：章节模板触发** | 用户选择文档类型 | 标准章节结构 + 预填充内容 | 新建文档时快速搭建框架 |
| **模式 C：需求关联触发** | 上传需求文件并提取要点后 | 与需求要点相关的知识库内容 | 方案生成阶段 |

#### 3.4.2 推送示例

```
用户输入："本项目按照等保2.0三级要求进行建设..."
         ↓
系统识别关键词："等保2.0"、"三级"
         ↓
自动推送：
- 【等保2.0三级通用要求】模板卡片
- 【等保测评流程说明】历史段落
- 【三级等保技术方案框架】章节模板
```

### 3.5 文档校对面板模块

**功能描述**：提供专业的文档检查面板，重点检查投标文档的风险项和规范性。

#### 3.5.1 校对检查项

| 检查类别 | 检查项 | 说明 | 优先级 |
|---------|-------|------|-------|
| **偏离分析** | 技术偏离表 | 逐条核对技术方案与招标要求的偏离项 | P0 |
| | 商务偏离表 | 逐条核对商务条款与招标要求的偏离项 | P0 |
| **风险检查** | 废标项检查 | 检测可能导致废标的致命错误（签字盖章、保证金、密封、有效期等） | P0 |
| | 敏感词检查 | 避免"保证"、"承诺"等商务风险词 | P0 |
| **格式检查** | 标点符号规范 | 中文标点、全角半角统一 | P0 |
| | 编号连续性 | 章节编号是否连续（1.1.1 → 1.1.2） | P1 |
| | 字体/段落格式 | 是否符合预设规范 | P1 |
| **内容检查** | 术语一致性 | 全文术语统一（如"等保"不混用"等级保护"） | P1 |
| | 数据准确性 | 公司名称、日期、金额前后一致性检查 | P1 |
| | 完整性检查 | 投标书必含章节（资质、报价、工期）与招标文件目录核对 | P1 |
| | 引用规范 | 标准号格式（GB/T XXXX-XXXX） | P2 |
| **智能分析** | 上下文合理性 | 基于语义分析内容逻辑是否合理 | P1 |

#### 3.5.2 偏离表检查详细规则

偏离表是投标文件的核心检查项，需逐条核对：

1. **提取强制要求**：从招标文件中提取所有带"★"、"必须"、"须"、"应"等强制要求的条款
2. **定位应答内容**：在投标文件中定位对应的应答段落
3. **判定偏离状态**：
   - 无偏离：完全满足（✓ 绿色）
   - 正偏离：优于要求（△ 蓝色，需确认是否可接受）
   - 负偏离：不满足（✗ 红色，高风险）
4. **生成偏离汇总报告**

| 偏离类型 | 判定标准 | 风险等级 | 处理建议 |
|---------|---------|---------|---------|
| 无偏离 | 完全满足招标要求 | 无 | 直接通过 |
| 正偏离 | 技术指标优于要求 | 低 | 需确认客户是否接受 |
| 微小偏离 | 非关键条款轻微差异 | 中 | 评估影响，准备说明 |
| 重大偏离 | 关键条款不满足 | 高 | 可能废标，需重点关注 |

#### 3.5.3 检查结果展示

- 左侧边栏展示所有检查项状态（通过 / 警告 / 错误）
- 点击问题项可跳转到文档对应位置（通过 Office.js 或手动定位）
- 提供一键修复建议（如替换标点、统一术语）
- 支持导出校对报告（PDF / Word）

### 3.6 自排版标题功能

**功能描述**：自动识别文档中的标题层级，按规范格式进行排版。

| 标题级别 | 字体 | 字号 | 对齐方式 | 段前段后 |
|---------|------|------|---------|---------|
| 一级标题 | 黑体 | 三号 | 居中 | 段前 1 行，段后 1 行 |
| 二级标题 | 黑体 | 小三 | 左对齐 | 段前 0.5 行，段后 0.5 行 |
| 三级标题 | 黑体 | 四号 | 左对齐 | 段前 0.5 行，段后 0.5 行 |
| 正文 | 宋体 | 小四 | 两端对齐 | 段前 0 行，段后 0 行 |

**自动识别方式**：
- 基于关键词（如"第 X 章"、"X.X"编号）
- 基于段落格式特征
- 基于语义分析（AI 辅助）

### 3.7 知识沉淀模块（脱敏入库）

**功能描述**：将新编写的高质量内容转化为可复用的模板资产。

**工作流程**：

```
文档编辑 → 脱敏处理 → 质量评估 → 加入模板库
    │           │           │           │
    ▼           ▼           ▼           ▼
完成新文档   自动识别敏感   人工确认/   设置标签
编写        信息并替换     评分决定     分类成为
                         是否入库     新模板
```

**脱敏规则**：

| 类型 | 示例 | 替换为 |
|-----|------|--------|
| 客户名称 | 中国工商银行 | 客户 A（国有大型银行） |
| 具体金额 | 5,800,000 元 | [项目预算：500-1000 万] |
| 具体日期 | 2024 年 3 月 15 日 | [项目启动时间] |
| 内部系统 | XX 核心系统 | 客户核心交易系统 |
| 人员姓名 | 张经理 | [客户方项目经理] |

**保留信息**：
- 行业特征（"零售业务占比高"保留）
- 技术架构类型（"分布式核心"保留）
- 项目规模描述（"涉及 32 个分行"保留具体数字）

## 4. 非功能需求

### 4.1 部署方式

| 方案 | 说明 | 选择 |
|-----|------|------|
| 桌面客户端 | Tauri 独立应用 | ✅ |
| Word/WPS 插件 | Office.js 任务窗格 | ❌（改为剪贴板桥接 + Office.js 可选轻量插件） |
| Web 应用 | 浏览器访问 | ❌ |

**选择理由**：
- Tauri 应用直接读写本地/NAS 文件，无需上传下载
- 单安装包部署，用户零配置
- 支持完整的本地 AI 能力（Ollama）

### 4.2 性能要求

| 指标 | 要求 | 说明 |
|-----|------|------|
| 应用启动时间 | ≤ 3 秒 | 从双击到界面可用 |
| 模板检索速度 | ≤ 2 秒 | 返回搜索结果（80GB 知识库） |
| 需求文件解析 | ≤ 5 秒 | 50MB 以内文档完成解析和要点提取 |
| 智能推送响应 | ≤ 1 秒 | 输入后推荐内容出现时间 |
| 文档检查速度 | ≤ 5 秒/万字 | 校对检查完成时间 |
| 草稿生成速度 | ≤ 30 秒 | 基于需求和知识库生成完整方案草稿 |

### 4.3 兼容性要求

| 项目 | 支持版本 |
|-----|---------|
| Microsoft Word | 2016 及以上 |
| WPS Office | 2019 及以上 |
| 操作系统 | Windows 10/11、macOS 12+ |
| NAS 协议 | SMB/CIFS、NFS、AFP |

### 4.4 安全性要求

- **默认本地优先**：所有数据处理优先在本地完成，NAS 文件不离开内网
- **AI 隐私模式**：默认调用本地 Ollama，数据不上传云端；仅在用户显式开启或本地资源不足时切换到云端 API
- **脱敏保障**：原始客户资料在本地处理，脱敏后才进入知识库索引
- **NAS 权限**：遵循企业现有 NAS 权限体系，不额外创建访问账号
- **无痕处理**：上传的需求文件解析后仅保留提取的要点文本，不存储原始文件

### 4.5 AI 自适应策略

| 场景 | 策略 |
|-----|------|
| 本地 Ollama 可用且响应正常 | 优先使用本地模型 |
| 本地 Ollama 未安装或模型未下载 | 提示用户安装，或询问是否切换到云端 |
| 本地 Ollama 响应超时（> 60 秒） | 自动降级到云端 API，并提示用户 |
| 用户显式选择"使用云端 AI" | 所有 AI 调用走云端 API |
| 生成超长文档（> 4000 token 输出） | 本地模型可能效果差，建议切换云端 |

## 5. 数据流与交互设计

### 5.1 核心工作流

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│ 1.需求上传   │ ──► │ 2.要点提取   │ ──► │ 3.知识检索   │ ──► │ 4.草稿生成   │
│   & 解析    │     │   (AI)      │     │   (Meili)   │     │   (AI)      │
└─────────────┘     └─────────────┘     └─────────────┘     └─────────────┘
                                                                  │
                                                                  ▼
┌─────────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│ 7.知识沉淀   │ ◄── │ 6.自动校对   │ ◄── │ 5.人工编辑   │ ◄── │  Tiptap    │
│  (脱敏入库)  │     │   (AI+规则)  │     │   & 完善    │     │  编辑器     │
└─────────────┘     └─────────────┘     └─────────────┘     └─────────────┘
```

### 5.2 数据流详细说明

**阶段 1：需求上传与解析**
1. 用户将文件拖入 Tauri 前端上传区
2. 前端通过 Tauri Command 将文件传递至 Rust 后端
3. Rust 后端保存到临时目录，调用对应解析库提取纯文本
4. 解析完成，返回文本内容至前端展示

**阶段 2：AI 要点提取**
1. 前端将文档文本发送至 Rust 后端 AI 客户端
2. AI 客户端优先调用本地 Ollama，若不可用则调用云端 API
3. 返回结构化 JSON（需求要点列表）
4. 前端渲染为可编辑勾选列表

**阶段 3：知识库检索**
1. 用户确认要点后，前端将每个要点作为查询词发送至 Rust 后端
2. Rust 后端调用 Meilisearch（内嵌进程）执行全文检索
3. 合并去重、排序，返回 Top-N 结果
4. 前端展示推荐列表，用户可选择引用

**阶段 4：草稿生成**
1. 用户点击"生成草稿"，前端组装 Prompt（要点 + 引用片段 + 框架）
2. 发送至 AI 客户端生成完整文档
3. 返回 Markdown，前端在 Tiptap 中渲染为富文本

**阶段 5：人工编辑**
1. 用户在 Tiptap 中编辑草稿（增删、改格式、调整内容）
2. 可随时触发"智能推送"获取写作建议
3. 编辑完成后点击"插入 Word"
4. 前端将富文本 HTML 写入系统剪贴板，提示用户粘贴到 Word/WPS

**阶段 6：自动校对**
1. 用户将 Word 中写好的文档内容（通过 Office.js 或手动复制）传回应用
2. 前端发送至 Rust 后端校对引擎
3. 校对引擎执行规则检查（偏离、废标、格式、术语）+ AI 语义分析
4. 返回问题列表，前端在校对面板中展示

**阶段 7：知识沉淀**
1. 用户完成项目后，选择"脱敏入库"
2. Rust 后端脱敏引擎执行正则替换（客户名、金额、日期等）
3. 用户确认脱敏结果，选择分类和标签
4. 保存至 SQLite 元数据库，并更新 Meilisearch 索引
